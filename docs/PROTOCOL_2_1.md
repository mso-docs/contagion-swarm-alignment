# Protocol 2.1: exploratory swarm-size scaling

This prospective amendment preserves RQ1/RQ2/RQ3 and the frozen five-agent experiments. Protocol 2.0 still requires five agents. Protocol 2.1 permits 5–128 logically isolated agents for RQ1; RQ3's matched five-call decomposition remains unchanged. Model agents stay tool-free and controller-mediated.

The initial ramp is 5,10,20,40,80 agents on the same seeded development scenario sample, keeping topology, intervention source/round, rounds, model digest, inference settings and scenario schedule fixed. Freeze each size's complete plan before inference and keep size cohorts separate. New sizes require explicit per-run and total call budgets. A fixed10,000 delivered-message ceiling rejects excessive complete-graph configurations. Calls are still serial by default; agent count does not imply simultaneous requests or more physical model instances.

Start with the checked-in ten-agent mock plan. No larger live ramp is authorized for unattended saturation of the shared primary server: establish a resource allocation with its other operator first. Do not change shared Ollama settings, restart the service or run an aggressive concurrency test. Small CPU-only neural smoke work on the secondary server is a separate workload.

Measure task success, unauthorized artifact behavior, exposures/messages and run/call latency by size. Number of opportunities, messages, token budget and graph diameter vary with size and confound pooled violation rates. With only two rounds, most ring nodes cannot be reached from the injection source; this is a short integration screen, not a fair end-to-end propagation comparison across sizes. A later propagation study must preregister its round/depth and exposure-matching choices (maximum five rounds remains unchanged). No model-independent alignment score is inferred.

Ollama's documented controls distinguish parallel requests (`OLLAMA_NUM_PARALLEL`), waiting requests (`OLLAMA_MAX_QUEUE`) and concurrently loaded models (`OLLAMA_MAX_LOADED_MODELS`). There is no documented universal60-agent limit. Identify the origin of any60 cap in the actual caller/service before adjusting it. GPU/context-memory headroom and observed latency/error rates, rather than network bandwidth alone, determine a sensible concurrency budget.
